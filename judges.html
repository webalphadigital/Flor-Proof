Full flow

  1. Grower: open "I'm a grower", enter the grower code and register a batch with your own new code, for example JUDGE-YOURNAME-01. You get a QR page.
  2. Open the QR: the status says "Pending confirmation".
  3. Florist: open "I'm a florist", enter the florist code, choose "Confirm receipt of a batch" and use the same batch code.
  4. Choose "Make a bouquet" with that batch code and a new bouquet code, for example JUDGE-YOURNAME-R1. Open the bouquet QR.
  5. Scan or open it: you see the full journey from grower to bouquet.

Batch and bouquet codes can be used only once (letters, numbers, dots, hyphens and underscores). A bouquet needs a confirmed batch. Transactions take a few seconds.

Flujo completo

  1. Productora: abrí "Soy productora", escribí el código de productora y registrá un lote con un código nuevo propio, por ejemplo JUEZ-TUNOMBRE-01. Recibís una página con el QR.
  2. Abrí el QR: el estado dice "Pendiente de confirmación".
  3. Florería: abrí "Soy florería", escribí el código de florería, elegí "Confirmar recepción de un lote" y usá el mismo código de lote.
  4. Elegí "Armar un ramo" con ese código de lote y un código de ramo nuevo, por ejemplo JUEZ-TUNOMBRE-R1. Abrí el QR del ramo.
  5. Escaneá o abrí ese QR: ves el recorrido completo, desde la productora hasta el ramo.

Los códigos de lote y de ramo se usan una sola vez (letras, números, punto, guion y guion bajo). Un ramo necesita un lote confirmado. Las transacciones tardan unos segundos.

Technical overview

Descripción técnica

Static frontend (GitHub Pages) → serverless backend (Vercel) → smart contract (Monad Testnet). Customers read directly from the contract, with no backend and no wallet.

Smart contract
  • Solidity ^0.8.24, one contract (FlorProof) on Monad Testnet: see links below.
  • An admin authorizes growers and florists; each role can only call its own functions.
  • declararLote: a grower records a batch. The batch ID is the hash of its code, so codes are unique. A hash of the data plus the grower's address is stored.
  • confirmarRecepcion: a florist confirms receipt. registrarRamo: links a bouquet to a batch, only for the florist who confirmed it.
  • registrarVenta: the grower decrements stock, never below zero (not in the interface yet).
  • consultarLote / consultarRamo: read-only. Declared data can't be edited later. Price and grower name aren't stored.
Backend
  • Node.js and ethers v6. Two functions: registrar (grower) and florista (florist).
  • Each access code maps to its own signing key, kept only in environment variables. The backend signs and pays gas, so users never touch a wallet.
  • Input validation, timing-safe code comparison, CORS limited to the frontend's origin, and contract errors decoded into clear EN/ES messages.
Frontend
  • Vanilla HTML/CSS/JS with ethers v6. Landing, grower form, florist form, public lookup and a QR page that saves the code as an image.
  • The lookup reads the contract through a public RPC: variety, origin, harvest and expiry dates, shelf life left, stock and receipt status. EN | ES interface.
Trade-offs and next steps
  • Signing is custodial to ease onboarding. Next: one wallet per grower with passkeys.
  • Authorizing growers and florists is a manual admin action. Next: an admin screen.
  • Testnet only. A mainnet deployment would start a new contract.

Frontend estático (GitHub Pages) → backend serverless (Vercel) → contrato inteligente (Monad Testnet). Los clientes leen directo del contrato, sin backend y sin wallet.

Contrato inteligente
  • Solidity ^0.8.24, un contrato (FlorProof) en Monad Testnet: ver enlaces abajo.
  • Un administrador autoriza productoras y florerías; cada rol solo llama a sus propias funciones.
  • declararLote: una productora registra un lote. El ID del lote es el hash de su código, así que los códigos son únicos. Se guarda un hash de los datos junto con la dirección de la productora.
  • confirmarRecepcion: una florería confirma la recepción. registrarRamo: vincula un ramo a un lote, solo para la florería que lo confirmó.
  • registrarVenta: la productora descuenta stock, sin bajar de cero (todavía no está en la interfaz).
  • consultarLote / consultarRamo: solo lectura. Los datos declarados no se pueden editar después. No se guardan el precio ni el nombre de la productora.
Backend
  • Node.js y ethers v6. Dos funciones: registrar (productora) y florista (florería).
  • Cada código de acceso corresponde a su propia clave de firma, guardada solo en variables de entorno. El backend firma y paga el gas, así que los usuarios nunca tocan una wallet.
  • Validación de entradas, comparación de códigos resistente a ataques de tiempo, CORS limitado al origen del frontend y errores del contrato traducidos a mensajes claros en EN/ES.
Frontend
  • HTML/CSS/JS puro con ethers v6. Inicio, formulario de productora, formulario de florería, consulta pública y una página de QR que guarda el código como imagen.
  • La consulta lee el contrato por un RPC público: variedad, origen, fechas de cosecha y vencimiento, vida útil restante, stock y estado de recepción. Interfaz EN | ES.
Compromisos y próximos pasos
  • La firma es custodiada para facilitar el alta. Próximo paso: una wallet por productora con passkeys.
  • Autorizar productoras y florerías es una acción manual del administrador. Próximo paso: una pantalla de administración.
  • Solo testnet. Un despliegue en la red principal empezaría con un contrato nuevo.
